# Lab 1 关键提示词记录

## 说明

本文件汇总 Lab 1 中真正影响实验方案、执行路径和验证结果的提示词。日常确认、催促继续、简单问答以及与实验无关的聊天没有收录。

下面的提示词以实际对话为依据做了结构化整理：补全了上下文、交付物、约束和验收条件，但没有改变原始意图，也没有把未发生的工作写进来。这样整理的原因是，口语化对话适合协作，却不便于复现；提交版提示词需要让另一个具备项目访问权限的 AI 明确知道输入、边界、输出和完成标准。

真实性边界如下：Prompt 1、2、3、4、7、8 分别对应学生在需求理解、风险确认、方案审查、授权执行、报告审校和交付整改阶段提出的实际要求；Prompt 5、6 是从已经确认的执行计划中抽取出来的技术子任务提示词，用于约束 QEMU 诊断和 GDB 取证。后两条不是伪装成学生逐字说过的话，而是长任务在执行阶段实际采用的结构化子任务。

## Prompt 1：先理解实验，再设计执行方案

### 使用阶段

首次接触 Lab 1，尚不清楚课程要求和代码结构时。

### 整理后的提示词

```text
这是操作系统课程的 Lab 1。课程明确允许并要求借助大模型完成实验，但我目前不了解实验目标、代码结构和验收要求。

可用资料：
1. 课程实验指导书：http://8.135.34.58/lab2026/_book/
2. 项目目录中的 lab1 源码；
3. 已提供的环境搭建文档。

请先不要修改代码或直接完成实验。先完成以下分析：
1. 阅读课程网页中 Lab 1 的实验目的、练习、项目结构、GDB 使用和报告要求；
2. 检查本地 Lab 1 源码，判断是否存在需要补全的函数或 TODO；
3. 说明最终交付物、两道练习分别要回答什么、需要取得哪些真实证据；
4. 区分课程文档中的通用原理、示例输出与本机必须实际验证的结果；
5. 给出分阶段执行方案，每阶段列出操作、预期结果、验证方法和停止点。

在我确认方案之前，不要正式实施，也不要撰写实验报告。不要把课程文档中的示例地址或输出冒充本机结果。
```

### 提示词设计说明

这条提示词先限制 AI 的行动范围，再要求它从网页、源码和环境文档三类输入交叉核对需求。验收条件不是“给出解释”，而是形成可执行、可验证、可暂停的方案。

## Prompt 2：评估环境变更风险

### 使用阶段

配置 WSL、交叉编译器和 QEMU 之前，电脑上仍有其他代码在运行。

### 整理后的提示词

```text
在开始配置 Lab 1 环境前，请先评估这些操作会不会影响我当前正在运行的代码和 Windows 日常使用。

请按以下类别说明风险：
1. 仅在 WSL/Ubuntu 内安装软件的影响；
2. 启用 WSL2、虚拟化或修改 Windows 启动配置的影响；
3. 是否需要重启，以及重启会中断哪些现有任务；
4. QEMU 编译或运行时的 CPU、内存和磁盘占用；
5. 哪些操作是可逆的，哪些操作执行前必须再次告知我。

先给出风险判断和安全执行顺序，不要在没有确认的情况下重启、终止未知进程或修改项目外文件。
```

### 提示词设计说明

这条提示词把“会不会影响电脑”拆成安装范围、系统设置、资源占用和可逆性四类问题，并明确了需要二次确认的高影响操作。

## Prompt 3：制定 Lab 1 的可验证实施计划

### 使用阶段

环境已经可用，但正式执行实验前需要先审查方案。

### 整理后的提示词

```text
请根据课程网页、本地源码和当前已经安装的工具，为 Lab 1 制定一份可审查的实施计划，先不要执行。

计划必须包含：
1. 环境基线：记录 Make、RISC-V GCC/binutils、GDB、QEMU 和 Ubuntu 版本；
2. 干净构建：从 make clean 开始，验证 kernel 与 ucore.img 确实生成；
3. ELF 检查：核对架构、入口地址和 kern_entry、kern_init、bootstack、bootstacktop 等符号；
4. 练习 1：用源码和 GDB 单步共同验证 la sp, bootstacktop 与 tail kern_init，记录 sp、ra 和栈大小；
5. 练习 2：使用全新调试会话验证 0x1000、0x80000000、0x80200000 三个阶段；
6. 模块分析：说明链接脚本、.bss、SBI 输出链和 ecall 的作用；
7. 报告所需证据：所有地址、版本和反汇编必须来自本机执行；
8. 清理：每次调试后确认没有遗留 QEMU 进程。

约束：
- 不修改 C/汇编功能代码，除非实际构建被工具版本兼容问题阻塞；
- 不运行仓库中不存在的测试脚本；
- 不伪造 make grade、截图、寄存器值或命令输出；
- 报告另行确认，本阶段只给计划。
```

### 提示词设计说明

重点是把抽象任务转换成“动作 + 观测量 + 完成条件”。例如，练习 1 不能只解释伪指令，而要同时记录符号地址、寄存器变化和真实反汇编。

## Prompt 5：诊断 QEMU 启动兼容问题

### 使用阶段

旧式加载参数能启动 OpenSBI，但无法进入内核时。

### 整理后的提示词

```text
当前 Lab 1 在 QEMU 8.2.2 上能够启动 OpenSBI，但没有进入内核。请按系统化调试方式定位原因，不要直接尝试随机参数。

已知课程网页使用旧式参数：
-device loader,file=bin/ucore.img,addr=0x80200000

请完成：
1. 记录失败时 OpenSBI 的 Domain0 Next Address 和 Next Mode；
2. 检查 ELF 入口、镜像生成方式和 Makefile 的 qemu/debug 目标；
3. 区分“QEMU 把镜像预装到内存”和“OpenSBI 获得下一阶段入口”这两个问题；
4. 查找适用于当前 QEMU/OpenSBI 组合的最小修改；
5. 修改后重新运行，只有同时观察到 Next Address = 0x80200000 和内核启动字符串才算修复；
6. 在最终说明中保留旧参数失败、新参数成功的证据，不把兼容修改描述成内核功能实现。
```

### 提示词设计说明

这里没有只说“QEMU 跑不起来，帮我修”。提示词给出了已知现象、待区分的责任边界和双重验收标志，减少了大模型反复更换参数的盲目性。

## Prompt 6：用 GDB 形成可复核的启动链证据

### 使用阶段

执行两道练习并准备报告证据时。

### 整理后的提示词

```text
请为 Lab 1 建立两组相互独立的 GDB 调试证据。

第一组验证内核入口：
1. 在 0x80200000/kern_entry 断下；
2. 记录 pc、sp、ra、bootstack、bootstacktop 及地址差；
3. 反汇编 kern_entry，说明 la 和 tail 的实际展开；
4. 按机器指令单步，记录 sp 何时等于 bootstacktop；
5. 进入 kern_init 前后比较 ra，判断 tail 是否建立返回链。

第二组验证完整启动链：
1. 重新启动停在复位状态的 QEMU；
2. 记录初始 PC 和 0x1000 附近真实指令；
3. 在 0x80000000 断下并记录 OpenSBI 入口指令；
4. 在 0x80200000 断下并记录内核入口指令；
5. 区分实际执行的 MROM 指令与被 GDB 强制反汇编的数据；
6. 不声称观察到了没有逐步跟踪的 OpenSBI 内部行为。

如自动化 GDB 命令存在 shell 转义或变量展开问题，废弃受影响的输出，从复位状态重新执行，不得用错误结果补写报告。
```

### 提示词设计说明

这条提示词要求将练习拆成两个干净会话，并提前规定错误证据的处理方式。实际执行时确实出现过 `$pc` 被外层 shell 展开的错误，随后按这套标准重新运行。

## 总结

这些提示词共同使用了四类约束：明确输入来源、限制 AI 权限、把任务拆成可观测步骤、用实际输出定义完成条件。实验中最有效的做法是提前规定“什么证据无效”：网页示例不能代替本机输出，错误转义产生的反汇编必须重跑，未观察到的固件行为不能写成事实。
