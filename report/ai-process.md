# Lab 2 AI 辅助分析与修正记录

我们一起将 AI 用于理解接口、提出测试条件和分析失败，再用源码与运行结果核对。10-21 初次实现过程依据原实验稿保留；10-22、10-25 补充审校、复测和源码调试记录。关键提示词的来源与提炼方式见 [prompt.md](prompt.md)。

## 1. 从任务理解到分配器实现

初次实现先围绕“物理页从哪里来、哪些页不能分配”梳理 DTB → `Page` 描述符 → 空闲区注册 → `pmm_manager`。由此把 `page_init` 的范围计算与具体分配策略分开检查。原稿记录了默认空闲区 `[0x80347000,0x88000000)`，后续 WSL 默认构建也得到该范围；起点仍由链接结果计算。

First-Fit 用于对照 Best-Fit：前者取首个足够大的块，后者扫描全部候选取最小足够块。AI 辅助列出属性、计数和前后合并条件，最终实现保持课程 `basic_check`、`best_fit_check` 不变。

重新对照完整练习页后，明确 Buddy 是任务三，SLUB 才是选做 Challenge。Buddy 因此独立接入管理器接口，默认保留 Best-Fit。实现提示词与测试提示词分开，分别规定分阶拆分/合并，以及容量、计数、对齐等检查。

## 2. 两次“只看到 OpenSBI”的原因不同

原稿记录的第一处问题是入口位于普通 `.text`，没有进入链接脚本优先放置的 `.text.kern_entry`；改用专用入口节，并使用 `-kernel bin/ucore.img` 交给 OpenSBI 启动。

10-22 在 QEMU 8.2.2 上复测时仍未进入 C 入口。此次入口节已经正确，不能重复套用旧结论。GDB 和异常跟踪显示：写入 `satp` 后，PC `0x80200038` 发生取指页故障。页表只有高地址映射，切换到高地址前的低地址指令却仍需执行。于是补上根索引 2 的恒等映射，保留索引 511 的高地址映射。复测随后到达 `kern_init` 并完成分配器检查。

这一步使我们具体理解了“开启分页”和“跳到高地址”之间仍存在指令执行窗口。失败证据见[核验索引](verification.md)。

## 3. 测试从计数恢复扩展到独立模型

原稿第一轮 Buddy 只检查释放后页数恢复，无法发现未合并的伙伴，于是加入各阶链表检查。后续又将真实分配器源码接到主机测试，用独立占用数组检查所有权和计数，固定种子 `2412744` 分别执行 20,000 次交错操作，并做非对齐起点、耗尽与逆序回收。Best-Fit 额外与独立计算的最小足够空闲段比较，ASan/UBSan 检查通过。

对 `page_init` 则在临时副本覆写 DTB 查询，覆盖零容量、错误基址、溢出、内存不足、页尾截断和零完整空闲页等 7 项。零空闲用例专门检查初始化结果，跳过要求申请成功的常规自检。这样能分别定位范围计算与分配策略的问题。

复核代码还修正了文字中的一个过强说法：Buddy 首页记录的是取整容量，能够核对阶数，却不能区分同容量的不同原始请求。

## 4. 构建和评分也要验证失败路径

WSL 首次评分暴露了 CRLF 换行问题，因而统一脚本与构建文件的 LF 约定。切换宏后可能复用旧目标文件的问题，则通过记录有效编译配置解决，不再依赖每次手动强制重编译。

评分改在独立临时副本中注入，保留课程测试，并传回编译失败。除了正常取得 20/20，我们还故意使用失败编译命令，确认脚本不会报成通过。10-25 又运行 14 项回归，覆盖三种管理器、不同 RAM 配置、恢复默认和评分原始内核标记。

## 5. 从客体页表检查推进到 QEMU 源码调试

最初客体 GDB 检查能读出 `satp`、根 PTE，并核对虚实地址字节，但看不到 QEMU 内部的 TLB 分支。对照分支任务后，另行准备官方 QEMU 8.2.2 的独立 debug 构建。AI 协助定位 `mmu_lookup1`、`riscv_cpu_tlb_fill`、`get_physical_address` 和 `tlb_set_page`，再通过条件断点过滤到目标访问。

为在 C 层同时观察命中与未命中，实际采用 TCI。客体执行两次加载，宿主单步记录查询分支、页表根和 PTE；Bare/Sv39 对比显示，Bare 不走客体页表，但仍经过 QEMU 软件 TLB。Sv39 在根层遇到 1 GiB 叶子，只读一个 PTE。这些结果对应报告中的调用路径与数值计算。

## 6. 双 GDB 的失败与修正

| 当时现象 | 分析、修正及核对 |
| --- | --- |
| QEMU 找不到镜像，参数中留有引号 | 检查宿主 GDB 的进程启动参数，改用已知工作目录下的相对镜像路径 |
| Bare 的首轮加载没有记录 | 对照客体 PC 与宿主断点启用位置，发现启用太晚；改到探针首次取指时启用 |
| 单步后物理地址仍是旧值 | `next` 停在多行赋值的续行，尚未完成写入；改在赋值后观察输出参数 |
| 调试器退出后仍有 QEMU | 本次 inferior 位于另一进程组；记录 PID，并核对二进制及端口后清理 |

上述失败摘录保留了来源与位置，见[日志摘录](evidence/2026-10-25-mmu-failure-excerpts.txt)。最终完整重跑同时取得宿主、客体完成标记，结构化记录含两种模式各四条观察，加载值正确，且没有遗留本次 QEMU。

AI 给出的函数和原因是查找线索；本次真正用于确认结论的是源码分支、寄存器/PTE 值、实际加载结果和回归日志。
